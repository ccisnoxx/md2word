## 3. 验证方法与范围

本任务只改变文档。优先复用仓库 `.venv` 已安装的 PyYAML，通过一次性内联脚本检查，不新增依赖或常驻校验工具。系统 python3 没有 PyYAML，不可把 ImportError 解释为文档解析失败。

| 检查 | 输入与通过口径 |
|---|---|
| 结构 | 读取新增 JSON/JSONL；用 `.venv/bin/python` 的 yaml.safe_load 解析受影响 frontmatter 和两个 docs YAML；字段类型及枚举符合 design，不能出现重复键。 |
| 链接 | 提取受影响文档的本地 Markdown 目标，按文档目录解析路径；验证新增链接的文件和标题锚点。既有与本任务无关的断链单独记录，不借机全仓修复。 |
| 事实 | 对照明确 owner／调用入口／配置／历史报告，逐项记录静态结论或报告声明；不把核验元数据作为自动通过证据。 |
| 状态保持 | 解析变更前后的产品 Manifest，对比 tasks 全体对象、status_values 和 rules，执行数据保持不变；旧 frontmatter 字段值保持，必要正文更正单独说明。 |
| 范围与卫生 | 只检查本任务新增内容及当前批次实际变更；路径使用相对形式。复用现有卫生工具显式文件入口检查新增任务材料，不启动全仓历史扫描或修改扫描规则。 |
| 工作区 | 与本任务建项前 baseline 比较 index 条目摘要和既有 dirty 文件内容；发生并发变化则解释来源，不能覆盖他人修改。 |

规划阶段命令：

```bash
python3 .trellis/scripts/task.py validate .trellis/tasks/11-10-documentation-evidence-governance
git diff --check -- .trellis/tasks/11-10-documentation-evidence-governance
```

任务文件尚未跟踪时，`git diff --check` 不覆盖其内容；必须同时用内联脚本检查任务目录文本的行尾空白、JSON/JSONL、引用和实际范围，不能只凭空 diff 声称通过。

实施阶段仅对实际改动文档运行同类定向检查，完成后由 Trellis check 子代理复核候选；不会运行应用测试、构建、OpenAPI 导出、CI、release/check 聚合器、Docker build/pull 或生产访问。
