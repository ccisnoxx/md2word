## 实施顺序

1. 重新检查工作区，保留其他并行改动，加载相关规范；核对错误码语义和现有中文映射，使用项目既有模式及安装类型。
2. Trellis implement 子代理负责共享诊断格式化、概览/诊断/异常中心接线和直接测试。主会话负责规划与 Spec；告知子代理并非独占工作区、不得回退他人修改，并要求中文汇报。
3. 增加已知原因和操作的中文解释，区分无诊断、无页码、具体根因未知；保留机器码、截断和多页语义。
4. 在失败任务概览使用同一摘要，不增加请求、不改变权限和动作。增加可验证实际消费/渲染的定向测试，不以源码字符串断言替代行为证据。
5. 仅在复现后端直接相关信息丢失时修复既有 owner；需要扩展合同则返回规划，没有后端问题不修改后端。
6. Trellis check 子代理复核实际差异与验收，仅修复实质问题；若实际修改脱敏/公共合同且仍有未决风险，追加独立只读复核。
7. 更新直接受影响 Spec，检查最终差异与工作区，报告证据及线上边界；提交前另给计划并请求确认，不自动推送。

## 最小有效验证

纯规划阶段只检查文档、上下文路径与 diff，不执行应用测试。

实现阶段按实际改动合并执行：

- frontend：`npm run test:unit -- src/utils/failureDiagnostic.test.ts`，覆盖中文原因、页码、缺失、截断、未知码；增加概览真实渲染/消费用例，覆盖 failed、非 failed 和旧响应。
- frontend：`npx --no-install vue-tsc --noEmit` 验证类型接线；不机械执行全量构建或 Playwright。实际布局改变时利用项目允许的已有渲染环境检查受影响视图，无法执行时如实记录。
- 后端定位需要新证据或实际修改时：`.venv/bin/python -m unittest tests.test_document_job_failure_diagnostic tests.test_render_failure_context`；触及消息策略时再执行 `tests.test_worker_failure_message tests.test_worker_failure_policy`。
- 不执行完整 backend 套件或聚合发布脚本。复用输入未变的成功结果；历史夹具失败单列，不扩大修复范围。

## 收尾边界

逐项记录 AC 证据。真实失败任务尚未提供，只能证明受测路径；生产访问、部署、重试不包含在本计划内，不创建 CI。非平凡 Python 改动需要同步检查 touched-scope 中文注释和开发者可见文本。
