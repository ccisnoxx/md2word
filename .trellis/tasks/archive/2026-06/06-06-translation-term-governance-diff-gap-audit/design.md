## Gap Findings

### Not a gap: first-version diff scope

The first-version scope requested by the roadmap is already present in current code and archived implementation records:

- read-only version diff
- read-only preflight
- read-only proposal compatibility preview
- structured conflict hints
- proposal review batch approve/reject
- governance/review page linkage

Reopening another implementation task with the same scope would likely duplicate existing behavior and increase regression risk.

### Non-blocking gap: browser-level regression evidence

The archived `translation-term-governance-diff` implementation records backend tests, OpenAPI export, full backend unittest, frontend build, and `git diff --check`. It also records that browser smoke was not run for that task because the prior tool session lacked Browser control and Playwright.

The later proposal linkage task did run real browser smoke for review/governance deep-link behavior, but there is still no focused browser smoke record for the Translation Term Set page rendering diff/preflight/proposal-compatibility with mocked data.

### Non-blocking gap: scale / pagination

Proposal compatibility preview filters pending proposals in service memory. That keeps first-version scope simple and is acceptable for current internal usage. If proposal volume grows, pagination or repository-level filtering should be split into a separate performance task.

### Non-gap: per-row Translation Term CRUD

逐条 Translation Term CRUD is not required for the first-version diff workflow:

- diff compares version/draft entries generated by existing CSV import and draft mechanics.
- conflict preview reads proposals and current draft state.
- review actions remain in proposal review, not in the set governance table.
- adding row-level CRUD would expand the contract and UI far beyond the current diff/preflight/preview goal.
