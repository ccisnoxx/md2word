## 测量口径

调用真实 `DocumentJobService.list_jobs`、`DocumentJobIncidentService.list_incidents`、`SqliteDocumentFileRepository.is_document_file_protected`、`DocumentFileRetentionPlanner.build_plan`。列表第一页、20 条、无筛选，任务列表 `created_at_desc`，异常中心 `updated_at_desc`；单保护测现存但未保护的失败源文件。清理只生成计划，不执行 mark_expired、删除预留或物理删除。

每格预热 1 次，计时 5 次，另执行 1 次外部计数和 1 次 tracemalloc 内存测量；播种、gc.collect、签名断言、输出和哈希不计入延迟。正常计时和内存阶段使用原 backend.connect，仅计数阶段添加 query_only/authorizer。经验 P95 使用 nearest-rank，5 次采样时等于最大值，不能当作稳定线上尾延迟估计。

SQL 数包含显式 BEGIN，另有 select_calls；不包含测试侧 EXPLAIN、防写 PRAGMA 或连接 API 的隐式提交。仓储次数为实际公开方法调用，不能与 SQL 数重复相加。返回行包含聚合结果与连接后页行；完整扫描量来自实际 EXPLAIN 中 SCAN 节点×表基数×调用次数，排除索引 SEARCH、临时 B 树、clock 常量，并非数据库引擎实测 rows_examined。当前错误检查无命中，分页排序遍历完整集合，推导成立；点查次数单列于原始 SQL。

tracemalloc 峰值只含请求期间 Python 分配，包括返回对象，排除播种与计数器，不覆盖 SQLite C 缓存。原始结果另有累计进程 RSS 高水位，它含导入、播种、全库哈希读取等先前阶段，不是单次请求新增 RSS，不能用它验收进程内存预算。VM 指令按每 1,000 指令回调给出下界，零不表示没有查询。

## 预算与处理建议

预算在正式结果之前写入 [design.md](design.md)。120 档沿用 1,000 档上限，10,000 容量档将延迟上限按任务数放大 10 倍；另单独检查固定 500ms 列表交互目标，不把宽松容量预算解释为用户体验达标。

| 路径 | 1,000档 P95预算 / 实际 ms | 10,000容量预算 / 实际 ms | Python峰值上限 MiB | 判断与最小后续方向 |
| --- | ---: | ---: | ---: | --- |
| 任务列表 | 500 / 62.181 | 5,000 / 620.718 | 32 | 1,000档结束；10,000固定500ms交互超限。若确有该容量要求，先核对真实MySQL计划，定位重复全扫/JSON计算；索引或持久化投影调整接入B08，不删既有正确性检查。 |
| 异常中心 | 500 / 110.544 | 5,000 / 1182.605 | 128 | 1,000档结束；10,000固定500ms交互超限。最小后续先评估同请求主件重复观察，再视收益设计分类/筛选下推，保留有效复核及快照语义；持久化变化接入B08。 |
| 单文件保护 | 50 / 0.370 | 500 / 1.618 | 32 | 三档预算均满足，建议结束，不引入索引或缓存。 |
| 保留期计划 | 5,000 / 387.507 | 50,000 / 22701.354 | 128 | 三档批处理预算均满足，建议结束。F×P增长保留为容量风险；若未来更严周期预算触发，可评估计划内一次读取保护集合，但删除时仍实时重核；映射索引须接入B08。 |

所有档位均满足设定的 Python 分配峰值上限和零正文读取要求。10,000 档异常中心 95.421MiB 接近 128MiB 上限的约75%，保留期计划 74.136MiB；更大的 payload、保护集合或并发会改变该结果，未以本样本证明进程总 RSS 可控。没有实施任何优化。

## 与生产的界限及验收
