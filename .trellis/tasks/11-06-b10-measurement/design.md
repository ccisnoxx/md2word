# 测量设计

## 边界和真实入口

调用现有 `DocumentJobService.list_jobs`、`DocumentJobIncidentService.list_incidents`、`SqliteDocumentFileRepository.is_document_file_protected`、`DocumentFileRetentionPlanner.build_plan`。这是 HTTP 对应业务读路径，不包含认证、中间件或 HTTP 序列化。清理仅测只读计划，不标记过期、不删除对象。

复用现有测试模型夹具与真实 SQLite 仓储；不创建完整应用 runtime，不读取 .env。所有物化数据文件放在本目录内，完成后仅清理本脚本创建的数据文件，不留下临时目录。

## 固定数据

采用 120、1,000、10,000 任务；固定时间与 ID，覆盖成功翻译、失败、运行、排队任务，含有效复核及已发布任务。按实际模型建立源文件/结果/IR 与 publication 保护关系；具体比例与字段分布在脚本及结果中明确，比例是合成假设，不能声称来自生产抽样。事件约 21 条/任务，对应用户提供的 2511/119 档位，只验证这些路径不读事件正文。文件不物化二进制内容，正文读取哨兵一旦调用即计数并报错。

确定的每 10 条任务分布：4 成功（2 已发布、1 有效 approved、1 有效 needs_fix），2 失败、2 运行、2 排队。每任务 1 源文件，成功任务另有 1 IR 与 1 DOCX；F=1.8N、P=0.2N、受保护文件=0.6N。三档分别为文件 216/1,800/18,000，publication 24/200/2,000，事件 2,520/21,000/210,000。任务与文件通过仓储创建、复核使用已有接口；publication 使用真实模型及仓储内部插入方法受控播种，事件模型批量 SQL 播种以免引入 21N 次无关提交，不将播种视为正式发布/事件写入验收。

单文件保护主测未保护源文件，确保完整扫描；另核对已发布文件命中。列表页大小 20、管理员可见全部任务，无日期和关键字筛选。该样本不代表所有表格/预览/新代深度动作分支，正文读取为零的结果只覆盖本次固定输入。

## 方法

数据构造、预热不计入请求耗时。每条路径至少 5 次无 tracemalloc 的计时，保存每次耗时，报告中位数、最小/最大值及经验 P95（小样本，不是线上 SLO 证据）。另做外部 SQL/仓储计数、EXPLAIN QUERY PLAN 和 tracemalloc 峰值测量；计数及内存测量不混入常规耗时。

5 次采样以 nearest-rank 计算经验 P95，即该组最大值；同时保留全部样本以便复查。SQLite progress handler 每 1,000 指令回调一次，其累计值仅是 VM 指令下界，不伪装为精确指令或扫描行数。数据库只读性由脚本保存前后状态证据。

SQL 返回行数、解码记录数、全扫描访问量必须分开。SQLite 执行计划与已知固定表基数用于推导完整扫描量，明确这是计划推导而非 MySQL rows_examined；SQLite VM 指令数可用 progress handler 记录。不能把聚合返回的一行算成扫描一行。保留逐 SQL 统计/计划，参数仅合成值。仓储包装不替换业务行为；不改全局时间语义，只将现有模块时钟固定在数据集时刻。

内存以 tracemalloc 的请求期间 Python 分配峰值为主，另记录进程峰值 RSS 并明确累计语义；SQLite 本机 C 缓存不能用 tracemalloc 代表。延迟、内存和扫描数字均只适用于固定数据和本地 SQLite。

## 预算与后续判定

预设 1,000 任务下任务列表/异常中心经验 P95 < 500ms，单文件保护查询 < 50ms，保留计划 < 5s；10,000 档作为容量增长观察，列出线性外推预算。读取正文应为零。内存预算按路径报告，暂定列表/保护 32MiB、异常中心/保留计划 128MiB Python 分配峰值。查询次数及扫描增长作为结构成本单列，不以常数 SQL 次数证明常数工作量。

为避免事后迁移预算，120 档沿用 1,000 档交互/批处理上限；10,000 档的容量预算按任务增长 10 倍设为列表/异常中心 5s、保护 500ms、计划 50s，Python 峰值内存上限保持不变。另列固定交互预算（列表/异常 500ms）是否满足，不把容量预算放宽解释为用户体验达标。

只报告最小优化建议。任何持久化索引、映射表或字段变更须进入 B08，并保留原发布/清理锁序与实时保护合同；不在本任务实施。
