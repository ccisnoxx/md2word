# 设计：先测量，再复用已有优化

当前结论：已按后续明确授权完成生产迁移、统一切换和线上验收，见[production-execution.md](production-execution.md)。下文保留设计/构建阶段边界，其未执行描述为当时快照。

## 边界与当前数据流

任务工作台：JobsPage → documentJobsApi.list → service.list_jobs → MySQL RR 只读快照 → query_document_jobs_sql → 页内动作。异常处理：IncidentTriagePage → incidents.list_incidents → 仓储全量 payload → 权限过滤和有效复核 → 分类/筛选/统计/排序 → 页内动作。两条路径不能用一项 SQL 优化概括。

前端已有 finally 清理和 50 秒请求超时。本阶段没有证据支持修改超时、轮询、loading 或路由；只有新运行证据证明前端缺陷才局部修复。

## 观测方案

优先用用户已登录的正常会话观察两页 GET 的状态、TTFB、总耗时和渲染完成时间，不提取或保存令牌，不重复登录或创建任务。后端测量仅记录阶段/查询编号、耗时、行数/字节数和调用次数，不保存业务 payload、SQL 参数、账号或私密文件名。

生产只读 GET 也有开销：串行、少量样本，遇到超时或明显负载异常停止重复采样。默认页先单次观察，确认可承受后至多三次；搜索和翻页按需要一次即可。需要服务器只读诊断时按当前授权和 personal-vps-ssh 技能核对目标；不在计划阶段启动服务、打开全局慢日志或写入线上配置。

本地替身可定位调用次数；真实 MySQL 的 JSON 解析/比较成本不能从 SQLite 时间推算。需要隔离引擎时先检查现有环境和资源边界，不能使用业务库或修改共享环境来补齐测试。

## 任务工作台的修复顺序

1. 冻结已部署版本和基线样本，复核 list-ready-once 的最终 diff/证据。该实现不是进程缓存：将完整校验合入请求内首条聚合，正常查询从 13 条 SELECT 变为 11 条；仍在同快照检查可见域和所关联文件，坏投影保持失败。
2. 得到该候选所有者的稳定交付后，在本任务隔离 checkout 中接入确切补丁；不修改来源 worktree。已获准在独立 checkout 接入稳定候选并定向验证。回退为移除候选局部差异，无数据库迁移。
3. 只有实际测量显示大 JSON 解析仍是主要瓶颈时，再评估 list-key-columns。保留完整规范文本比较；不以 hash、截断或旧 JSON fallback 改变语义。该候选改变 schema 和投影版本，需独立 MySQL 证据、已有迁移设计及单独生产窗口授权。
4. 两候选都影响 document_job_list_query.py 的 shape/文本读取/缺列错误和 specs，不能仅机械合并；整合后必须同时保留新版本和五列检查、请求内校验、错误优先级、原寻址 collation 与二进制业务比较。不得拿各自独立通过结果代替整合验证。

## 异常列表的修复顺序

先分别测量 list_document_jobs 的全量读取和模型解码、list_visible_jobs 的首次有效复核、classification 的主件读取与有效复核、分页动作。对有 verified 绑定的完成任务，_effective_job 和 _build_result_read_view 可分别访问同一文件，但它们的观察时点与完成态门控不同。

既有回归明确要求：分类开始前到期应按分类时刻失效；分类后到期不得让页内条目与统计分离；未完成任务保留 result 指针不能据此新增读取。首次有效复核可能已改变 review_status，不能无证明改为 raw job。禁止简单跨阶段缓存 file/最终分类，禁止删除首次观察后假定结果等价。

因此异常列表的具体代码候选是证据驱动的后续步骤：只在已证实瓶颈和上述约束内做局部改动；如果优化必须改变观察语义、增加仓储批量合同、数据库列或全量 SQL 下推，应先补充本设计并重新提交规划审核，不能以本任务授权自动扩大。即使普通列表提速，异常列表仍未达标时也不能关闭本任务。

## 验证和回退

冻结改前实现作为独立结果对照，使用真实既有业务 owner 和定向夹具；保留现有默认深度发布验证、异常诊断、批量操作、POST 重核。只有候选触及读取时序/共享合同，才安排独立只读 trellis-check 复核实际 diff。

当前进入本地实施，生产变更和回退另行授权。后续无 schema 修改可按任务补丁回退；拆列上线不能只换旧镜像，其回退需停写、旧版派生事实重建和全量核验，沿用独立任务的已写方案且另行授权。

## 2026-11-07 实施证据与候选选择

线上浏览器三个普通首页 GET 中位数 13.192 秒，异常首页中位数 2.351 秒，均 200；准确页面完成计时未取得，不能把 API 耗时当渲染验收。只读后端诊断确认普通列表 13 条 SQL 合计 11.420 秒，其中两个独立 shape 5.298 秒；投影最大约 2.38 MB。异常全量读取/解码仅约 0.079 秒，分类 1.944 秒，其中 68 次主件 get 合计 1.450 秒。

在独立 MySQL 8.4.13 的 119 jobs / 1,928 files 合成样本，ready-only 默认页三次中位数 6.444 秒，旧版 6.856 秒；合并首条仍 2.585 秒。完整结果等价，但净收益仅约 6%，满足原计划的拆列评估条件，故本地整合已有 key-columns 候选。保留完整二进制文本比较、五列 NULL 拒绝、版本 3/2，以及 ready 的请求内 V 域检查；不恢复两表独立全表扫描。

源候选的生产执行、游标与回退约束冻结在 [迁移设计副本](research/key-source-design.md)，内容 SHA-256: `c2198d837864b0c69d8bdf02a1b7a8ce15a39b1be627b40fcdab89f03ce5f508`。副本里的 assert_ready 调用位置描述属于单独 key 候选；当前整合以本设计的请求内 V 域检查为准。生产需要停写、备份恢复验证、显式实例/库核对、双表回填和空游标 verify；旧镜像不能直接回退，必须用冻结旧工具重建旧 JSON。上述生产操作本轮均未获授权、未执行。

异常列表的严格局部优化未找到：直接跳过已证明非异常的成功任务，会省去可达的文件解码、ID 校验、naive/aware 和保护关系查询错误。因此初始阶段未修改异常产品代码；随后补充请求级连接复用方案，用户于2026-11-07明确批准后实施，见下节。未采用缩小错误覆盖或跳过观察的方案。

## 异常下一阶段补充方案（2026-11-07 已批准）

后续只读细分已确认92次物理建连合计1.78秒，诊断额外设置仅0.10秒；建议采用[请求内连接复用方案](incident-read-session-plan.md)，保持每个原仓储操作独立事务、业务错误与时钟观察。独立架构复核确认可避免全局池、长事务及service克隆；用户已批准本地实施与定向验证，必须保持事务边界、错误处理和观察语义；提交、推送、生产变更仍另行确认。
